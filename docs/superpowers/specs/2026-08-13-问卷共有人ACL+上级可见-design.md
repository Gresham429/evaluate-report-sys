# 设计：问卷共有人（ACL）+ 上级可见（钉钉组织架构）

- 日期：2026-08-13
- 状态：**设计定稿、待实现**。用户已敲定：共有人 + 上级都要；共有人由**现场估价师在小程序选**；上级 = **部门主管 + 往上整条链**。
- 承接：#3（权限/`visibility_filter`）、`2026-08-13-办公端钉钉扫码登录`（真身份 userid）。**依赖登录**：本特性要真 userid 才有意义。
- 定位：把 #3 的「自己 / 全部」两档，升级成「**共有人名单（ACL）+ 上级层级 + 管理员**」。

---

## 0. 需求与关键约束

- 一份问卷的**持有者可能 2-3 人**，且**不一定同部门**（跨部门共有）——纯部门树盖不住，必须**显式共有人名单（ACL）**打底。
- 之上叠「上级看下属」：某共有人的**部门主管、以及往上整条链**的主管都能看。
- 仍是**办公端配合式**过滤（办公端应用凭据能读全表、主动只给你看你该看的），**非钉钉硬强制**（用户已知悉、接受，选的就是这层）。

## 1. 可见性规则（唯一真相）

对登录用户 `U` 与问卷 `S`：
```
可见(U, S) ⟺  U ∈ S.共有人
             或  S.共有人 ∩ 下属集(U) ≠ ∅        # U 是某共有人的上级（部门主管往上整条链）
             或  U ∈ OFFICE_ADMINS               # 管理员看全部
```
其中 `下属集(U)` = U 作为主管的所有部门、**及其所有子孙部门**的全体成员 userid（往下展开）。等价于「往上整条链」：owner 在部门 D，则 D、D 的父、父的父… 各级主管都能看。

**从简单 filler 过滤升级为逐份 ACL 判定**：不再是 `填报人==你` 一个等式，而是对每份候选问卷算上面的谓词。

## 2. 数据模型：共有人

- 问卷行**新增一列 `共有人`**（与 `填报人` 平铺并列；多维表列是文本，存 **JSON userid 列表**字符串，如 `["10076","01216..."]`）。
- `填报人` 保持不变 = **创建人/主填报**（单个，展示与"谁建的"用）。`共有人` = 含填报人在内的**全体可见持有者**。
- 记录契约在两处同步：`serverless/survey_broker/record.py`（vendored）+ `src/questionnaire/`（`model.py`/`backend.py`）——**加列要两侧同步**，契约测试拦漂移。
- `SurveyResponse` 加 `共有人: tuple[str, ...]`；`content_to_fields`/`response_to_fields` 加该列；旧行无此列 → 兜底 `[填报人]`（迁移友好）。

## 3. 组织架构模块 `src/dingtalk/org.py`（新）

职责：回答「`下属集(U)`」。接钉钉组织架构，**HTTP 可注入**（单测假件），端点标「# 待真机校准」。

- **取 U 主管的部门**：`topapi/v2/user/get {userid}` → `leader_in_dept:[{dept_id, leader}]`（U 在哪些部门是 leader）。
- **部门树往下展开**：`topapi/v2/department/listsub {dept_id}` 递归拿所有子孙部门。
- **部门成员**：`topapi/user/listid {dept_id}` 拿部门直属成员 userid。
- `下属集(U)` = ∪（U 主管的每个部门 + 其所有子孙部门）的成员 userid。
- **缓存**：部门树 + 成员变动不频繁；进程内缓存 `下属集(U)`（按 U，带 TTL，如 10 分钟），避免每次请求打一串钉钉接口。首次登录后算一次。
- 端点/字段路径按现行钉钉文档写，**真机一次校准**（同免登）。

> **「往上整条链」的实现**＝下属集往下展开子孙部门（U 管 D 就看 D 及其所有下级部门的人）。这与「owner 的各级上级都能看」等价，只需从 U 侧往下算一次，不必对每个 owner 往上回溯。

## 4. 办公端可见性重写

- `session.visibility` 从「返回一个 filler 字符串」升级为「返回一个**可见性判定器**」：
  - 管理员 → 看全部（等价现在的 `None`）。
  - 否则 → 判定器 `can_see(owners: list[str]) -> bool`：`U in owners or (set(owners) & 下属集(U))`。
  - `""`（认不出人）→ 恒 False（fail-closed）。
- `SurveyPullBackend` 的 list/pull/审核/回写全改用「按 owners 判定」而非 `填报人==filler`：
  - `list_submitted/list_pending`：逐行取 `共有人`，`can_see(共有人)` 才收。
  - `load`：命中 ID 后再 `can_see(共有人)`，否则当不存在（KeyError）。
  - `review/finalize`：逐条 `can_see` 才允许改状态（越权跳过、报「未找到」不泄露）。
  - 双向同步的 `writeback`（若已实现）同样按 `can_see` 授权。
- 下属集 U 由 `org` 模块算并缓存；管理员短路（不必算下属集）。

## 5. 小程序：加共有人（选人）

- 填问卷时**从钉钉通讯录选 2-3 个共有人**：用钉钉小程序选人 API（`dd.complexChoose` / `dd.chooseDepartmentEmployee` 之类，**具体 API 待钉钉开发者工具校准**）→ 拿被选人的 userid → 存 `content`/草稿的 `共有人`。
- 提交/保存时 `共有人`（含填报人自己）随 broker `saveDraft`/`submit` 写进问卷行。
- 显示：表单里列已选共有人、可增删；填报人自己默认在内、不可删。

## 7. 测试策略

- `org.py` 单测：假组织树（部门树 + 成员 + 主管），验 `下属集(U)` 递归展开正确、缓存命中。
- 可见性谓词单测：U∈共有人 / U 是上级 / 跨部门共有人 / 管理员 / 认不出人 fail-closed。
- 契约测试：`共有人` 列两侧编码一致。
- 办公端端点单测：list/pull/审核 按共有人+下属集过滤（假 org）。
- broker store 单测：`saveDraft` 写 `共有人`。
- 小程序 harness：选共有人 → 随提交带上。
- **真机门**：钉钉组织架构接口（user/get、department/listsub、user/listid）+ 小程序选人 API 各校准一次；broker 重部署 + 小程序重传；跨部门共有 + 上级可见实测。

## 8. 分期

- **P1｜共有人 ACL（无组织架构）**：数据模型 `共有人` + 小程序选人 + 办公端按名单过滤（`U ∈ owners` or admin）。**先解决"多人持有、跨部门"这个核心痛点**，不碰组织架构。需 broker 重部署 + 小程序重传。
- **P2｜上级层（组织架构）**：加 `org.py` 下属集 + 判定器叠加。校准最重、依赖钉钉部门接口。
- 交付前：`/code-review ultra` + 真机全链路。

## 9. 依赖与顺序（重要）

- **依赖扫码登录**（真 userid）——否则 `.env` 过渡身份下下属集无意义。
- **与双向同步耦合**：两者都碰 survey owner/可见性；若两个都做，`共有人` 字段与 `visibility` 判定器需一次设计到位，避免来回改。建议：**先落双向同步的字段/合并地基，或先落本特性的 `共有人`，二选一先行**，另一个在其上叠。
- 规模：本特性（尤其 P2 组织架构）是目前所有在途特性里最大的一件。
