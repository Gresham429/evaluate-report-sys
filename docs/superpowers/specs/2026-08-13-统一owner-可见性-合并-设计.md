## 1. 记录形状（多维表「实勘问卷」行）

平铺列：`问卷ID / 状态 / 填报人 / 共有人 / 更新时间 / 类别 / 问卷内容(JSON)`

- **填报人**：创建人（单个，展示"谁建的"）。不变。
- **共有人（新列）**：userid **列表**（JSON 字符串），含填报人在内的全体持有者。现场估价师小程序选；**任何共有人都能再加**（并发可编辑 → 见 §4 并集合并）。可见性/权限**都以共有人为准**，不再用填报人。
- **问卷内容**：`basic / subjects / subject_levels / asset_conditions / photos / gps`（不变）。
- 记录契约两侧同步（`serverless/survey_broker/record.py` + `src/questionnaire/`）；旧行无「共有人」→ 兜底 `[填报人]`。

## 2. 三种权限（唯一真相）

对登录用户 `U` 与问卷 `S`（`owners = S.共有人`）：

| 权限 | 谁有 | 用在哪 |
|---|---|---|
| **可见（读）** | `U∈owners` 或 `U 是某 owner 的上级` 或 `admin` | 出报告列表 / 拉取预填 / 审核列表 |
| **可编辑**（改内容 + 加共有人 + 发起审核） | `U∈owners` 或 `admin` | 回写问卷 / saveDraft / 发起审核(已提交→待审核) |
| **可定稿**（待审核→已定稿） | `U 是某 owner 的上级` 或 `admin` | 审核通过(定稿) |

要点：
- **上级只读内容**：能看、能**定稿**（=部门领导审下属，#3 §5 占位在此落地），但**不改内容**。
- **发起审核是 owner 的动作**（估价师做完报告提审）；**定稿是上级/admin 的动作**（审批）——发起与批准分离。
- `""`（认不出人）一律 False（fail-closed）。
- 「上级」= owner 所在部门主管、及部门树**往上整条链**（`org.py` 算 `下属集(U)`：U 主管的部门及所有子孙部门成员；`owners ∩ 下属集(U) ≠ ∅` 即 U 是上级）。P1 无 org 时无上级，定稿只 admin。

## 3. 内容合并（3-way，双端对称）

办公端回写 与 小程序保存 **走同一套**（`merge_content` 放共享 record 契约、契约测试钉死）：
- 叶子键：`basic.<k>` / `subject_levels.<因素>` / `asset_conditions.<因素>`。
- 逐叶子：我没动→取线上；线上没动→取我的；**同字段双改**→记冲突（弹窗逐字段选，见双向同步 spec §5）。
- `photos/gps/subjects`：办公端不碰 → 恒取线上（保留对方新加照片等）。
- base 快照（办公端草稿存 `survey_id`+载入时内容+更新时间）供 3-way 的 base。

## 4. 共有人合并（并集）

共有人是可并发编辑的列表（双方都可能加人），**用并集**：
- `merged_owners = union(mine_owners, theirs_owners)`（双方加的都留；并集不需 base）。
- **删除**：仅管理员显式删（罕见）；与并发的"加"相撞时，并集会让"加"赢——**已知简化**，可接受（删是刻意管理动作、极少并发）。
- 填报人恒在 owners 内、不可移除。

## 5. 写入路径（统一，办公端回写 + 小程序保存 同构）

1. **鉴权**：`can_edit(owners)`（`U∈owners or admin`）——不能编辑你无权改的问卷（上级来写→拒）。
2. **读线上** = theirs。
3. **合并**：`merge_content(base, mine, theirs)`（内容）+ `union(mine.共有人, theirs.共有人)`（共有人）。
4. **冲突**：内容有同字段冲突 → 不写、回 `{status:'conflict', conflicts}`，前端/小程序弹逐字段选 → 带 resolutions 重提。
5. **写** merged（问卷内容 + 共有人 两列）+ 刷新更新时间。回写不改状态。
6. `待审核/已定稿` 锁定态：拒写（沿用 #3 broker `_LOCKED_STATUSES` + 办公端回写端点 400）。

## 6. 可见性/权限落到各端点（重写 #3 的 filler 过滤）

`session` 从「返回 filler 字符串」升级为**三个判定器**：`can_see(owners)` / `can_edit(owners)` / `can_finalize(owners)`（各自 admin 短路；上级用 `org.下属集(U)`）。

- `/api/survey/list`（已提交，出报告）、`/api/survey/review/list`（待审核）：逐行 `can_see`。
- `/api/survey/pull`：命中 ID 后 `can_see`，否则当不存在（404）。
- `/api/survey/review`（发起审核）：`can_edit`。
- `/api/survey/finalize`（定稿）：`can_finalize`。
- `/api/survey/writeback`（回写，双向同步）：`can_edit` + 合并（§5）。
- broker `saveDraft`：`can_edit` + 合并（手机端）。

## 7. 小程序：选共有人

- 填问卷时从钉钉通讯录选共有人（`dd` 选人 API 待校准）→ userid 入 `共有人`；填报人默认在内、不可删。
- 已提交后任何共有人可再加（随 saveDraft 带上 → broker 并集合并写入）。

## 8. 组织架构 `src/dingtalk/org.py`

`下属集(U)` = U 主管的部门（`user/get.leader_in_dept`）及所有子孙部门（`department/listsub` 递归）的成员（`user/listid`）并集，进程内缓存带 TTL。端点待真机校准。详见共有人ACL spec §3。

## 9. 实现顺序（一条不返工的线）

1. **数据地基**：`共有人` 列（record 契约两侧 + `SurveyResponse` + 兜底 `[填报人]`）+ 办公端草稿存 base 快照。
2. **可见性/权限重写（P1，无 org）**：`can_see/can_edit/can_finalize`（P1 里上级恒空、定稿只 admin）+ 各端点改用之 + 小程序选共有人 + broker 写共有人。→ **先解决"多人持有、跨部门可见 + 只看自己/管理员"**。
3. **回写 + 合并（双向同步）**：`merge_content` + 共有人并集 + `/api/survey/writeback` + 小程序 saveDraft 合并 + 冲突UI。授权用 §2 判定器。
4. **上级层（ACL P2，org）**：`org.py` 下属集 → `can_see` 加"上级可见"、`can_finalize` 加"上级可定稿"。
- 1→2 是纯办公端+小程序/broker 数据面；3 叠合并；4 叠组织架构。每步都能独立测/上。

## 10. 测试与真机门

- 契约：`共有人` 列两侧编码一致。
- 权限：三判定器各分支（owner/上级/admin/认不出/跨部门共有）。
- 合并：内容 3-way 各分支 + 共有人并集 + 冲突。
- 端点：list/pull/发起审核/定稿/回写 各按对应判定器。
- 真机门：broker 重部署 + 小程序重传；钉钉选人 API + org 接口校准；跨部门共有 + 上级可见/定稿 + 双端并发改（不同字段自动合并、同字段弹窗）实测；`/code-review ultra`。

## 11. 仍是办公端配合式（非钉钉硬强制）

本模型再丰富，也是办公端应用凭据能读全表、**主动只给你看你该看的**——非钉钉层硬强制。一人一机内部自用够，用户已知悉接受。
