# 设计：问卷 ↔ 报告 双向同步（字段级三方合并）

- 日期：2026-08-12
- 状态：**设计定稿、待实现**。用户已敲定：双向同步（办公端可回写问卷）、双端「已提交」都可改、字段级三方合并、**同字段冲突弹窗逐字段选**、**一次做完两期**（办公端 + 手机端）。
- 承接：`2026-07-21-审核定稿+办公端钉钉登录+权限-design.md`（#3）。本特性建在 #3 的四态状态机（草稿→已提交→待审核→已定稿）与权限（`visibility_filter()`）之上。

---

## 0. 要解决的「割裂」（真机测试暴露）

办公端「从实勘问卷拉取」后：
1. **无链接**——报告草稿里不存 survey_id，问卷与报告草稿失联，看不出哪份问卷已被拉过。
2. **重复草稿**——每次拉取都 `draftId=null` → 新建一份草稿，同一问卷拉三次＝三份「未完成草稿」；生成报告后草稿也不清。
3. **编辑去向不明**——拉取后编辑的是办公端**本地报告草稿**，无「同步回问卷」的出口，估价师以为改动丢了。

根因：办公端把问卷当**一次性只读预填种子**，而用户要的是**问卷与报告双向绑定、编辑能回写问卷**。

## 1. 范围与非目标

**做：**
- 办公端草稿记 `survey_id` + 底版，**拉取幂等**（同一问卷回到同一份草稿）。
- **三方合并函数**（共享 record 契约，broker 与办公端同一套）。
- 办公端 **「保存回问卷」** 回写（读线上→合并→写）。
- **同字段冲突逐字段解决 UI**（办公端 + 手机端）。
- 手机端保存「已提交」问卷时**对称走同一套合并**。

**非目标（明确不做）：**
- 报告产物（一览表 `subjects`、选实例、比较法算价）**不回写问卷**——那是报告侧数据、不属问卷字段（铁律 #7）。
- 实时推送/长连接——无常驻服务器，仍是「读-合并-写」拉动式。
- `待审核 / 已定稿` 的内容编辑——沿用 #3 的锁（双侧只读、broker 拒写）。回写只在 `已提交` 态允许。
- 回写**不改问卷状态**——状态流转仍只由审核流程（发起审核/审核通过）做。

## 2. 合并字段空间（精确）

问卷内容 JSON 六键：`{basic, subjects, subject_levels, asset_conditions, photos, gps}`。经 `survey_to_prefill`（`src/questionnaire/prefill.py`）实测：

| 字段 | 办公端 | 手机端 | 回写处理 |
|---|---|---|---|
| `basic`（19 项 `SURVEY_FIELDS`） | 可编辑 | 可编辑 | **参与合并** |
| `subject_levels`（逐因素档次） | 可编辑 | 可编辑 | **参与合并** |
| `asset_conditions`（逐因素描述） | 可编辑 | 可编辑 | **参与合并** |
| `photos` | 不surface | 采集页编辑 | 办公端恒取线上（不回写） |
| `gps` | 不surface | 采集页编辑 | 办公端恒取线上（不回写） |
| `subjects`（一览表） | 报告侧编辑 | 恒 `[]` | 报告产物，恒取线上（不回写） |

即办公端回写只覆盖 **basic / subject_levels / asset_conditions** 三块；photos/gps/subjects 由合并「我没动→取线上」自动保留。

## 3. 三方合并函数（核心）

放共享 record 契约：`serverless/survey_broker/record.py`（vendored，仅标准库）+ `src/questionnaire/` 镜像；**契约测试对拍两侧字节一致**（broker 与办公端合并结果必须相同）。

```
merge_content(base, mine, theirs) -> (merged, conflicts)
```

- **叶子键空间**：`basic.<每键>`、`subject_levels.<每因素>`、`asset_conditions.<每因素>`（三个 dict 的键并集）。
- **逐叶子规则**：
  - `mine[k] == base[k]`（我没改）→ 取 `theirs[k]`；
  - `theirs[k] == base[k]`（对方没改）→ 取 `mine[k]`；
  - 三者互不相等（**同字段双改**）→ 记入 `conflicts`（`{field, label, base, mine, theirs}`），`merged[k]` 暂占 `mine[k]`，待上层按用户选择覆盖。
- `photos/gps/subjects`：不在叶子空间；`merged` 直接取 `theirs`（保留线上，含对方新加的照片）。
- **快捷路**：`base_mtime == theirs_mtime`（没人动过线上）→ 直接返回 `(mine, [])`，免逐字段。

合并是纯函数、无副作用、不触网——单测能穷举分支。

## 4. 链接与去重（办公端草稿）

办公端草稿 `数据` JSON 增三个键：
- `survey_id`：拉取来源问卷 ID（无＝手工/Excel 建的，不显示「保存回问卷」）。
- `survey_base`：拉取时的问卷内容快照（＝合并底版 `base`）。
- `survey_base_mtime`：底版的 `更新时间`（快捷路用）。

**拉取幂等**：`/api/survey/pull` 或前端拉取时，先按 `survey_id` 查本地草稿——
- 命中 → 回到该草稿；若线上 `更新时间` 比 `survey_base_mtime` 新，提示「问卷已更新，已刷新底版」并更新 base（不覆盖办公端未保存的表单改动，同手机端 `reconcileFromServer` 的护法）。
- 未命中 → 新建草稿，记 `survey_id/base/base_mtime`。

问卷列表（出报告页的 picker）标注：`已拉过`（本地有该 survey_id 草稿）/ `未拉过`。

## 5. 办公端回写流程

**入口**：出报告页，仅当当前草稿有 `survey_id` 时显示 **「保存回问卷」** 按钮（与「下载报告」并列、互不绑定，各可单独重复点）。

**端点** `POST /api/survey/writeback`：
- body：`{survey_id, base, mine, resolutions?}`
  - `mine` = `base` 叠上办公端表单当前值（basic/subject_levels/asset_conditions）；photos/gps/subjects 用 base 原值。
  - `resolutions`（可选）：`{field: 选定值}`，冲突弹窗解决后二次提交带上。
- 服务端：
  1. 权限：`visibility_filter()`——普通只能回写自己（`填报人==自己`）的问卷、管理员任意；否则 404（不泄露）。
  2. 状态：读线上，若 `状态 ∈ {待审核, 已定稿}` → 400「审核中/已定稿不可回写」。
  3. `theirs` = 线上当前内容。`merge_content(base, mine, theirs)`。
  4. 有 `resolutions` → 把选定值覆盖到对应冲突字段，视为已解决。
  5. 仍有未解决冲突 → **不写**，返回 `{status:'conflict', conflicts, theirs_mtime}`。
  6. 无冲突 → `update_record` 写 `merged`（整份 `问卷内容` JSON 列，含合并后的 basic/subject_levels/asset_conditions 与保留的 photos/gps/subjects）+ 刷新 `更新时间`，返回 `{status:'saved', merged, merged_mtime, applied_theirs_count}`。
- **回写不改状态**，只改内容与更新时间。

**前端**：
- 无冲突 → 提示「已保存回问卷（合并了对方 N 处改动）」；把本地 `survey_base` 更新为 `merged`、`survey_base_mtime` 更新。
- 有冲突 → 弹**冲突解决弹窗**：逐字段列「字段名 / 你的值 / 线上值」，单选留哪个（默认选「你的值」）；全部选完 → 带 `resolutions` + 解决时读到的 `theirs_mtime` 二次 POST。
  - 二次 POST 时线上又变了（`theirs_mtime` 不符）→ 服务端重新合并、可能再回冲突（罕见，如实再弹）。

## 6. 手机端对称合并（Phase 2，须重部署）

手机保存/提交**已提交**问卷时也走同一套合并，防手机保存冲掉办公端刚回写的其它字段：
- 手机 `base`：`loadDraft`/`reconcileFromServer` 时存下服务端内容作底版。
- `saveDraft` payload 增 `base`（+ 可选 `resolutions`）。broker `store.py`：
  - 记录已存在 → 读当前=`theirs`、`merge_content(base, mine, theirs)`；有冲突→返回 `{status:'conflict', conflicts, ...}` 不写；无冲突→写 merged。
  - 记录不存在（新草稿）→ 照旧 insert。
- 小程序新增**冲突解决页/弹层**：拿 broker 返回的 conflicts 逐字段选 → 带 resolutions 重发 saveDraft。
- 合并成功后手机把 `base` 更到 merged。
- **须 broker 重部署 + 小程序重传**。

## 7. 与 #3 状态机/锁的关系

- 回写/合并只在 `已提交` 态发生；`草稿` 是单侧（一般一台设备）也走合并（`theirs==base` 时快捷路即 mine）；`待审核/已定稿` 沿用 #3 的锁：手机只读、broker `_LOCKED_STATUSES` 拒写、办公端回写端点 400 拒。
- 回写不触碰 `状态` 列；发起审核/审核通过仍是唯一的状态流转口。

## 9. 测试策略

- `merge_content` 单测：我改/对方改/都没改/**同字段冲突**/不同字段并发/photos-gps 保留/快捷路。
- 契约测试：broker 与办公端 `merge_content` 对同一 (base,mine,theirs) 输出一致。
- 办公端 `writeback` 端点单测：无冲突合并写、冲突返回不写、resolutions 提交、权限（普通/管理员/非本人）、锁态（待审核/已定稿）拒写、幂等重复回写。
- broker `store` 单测：saveDraft 合并、冲突返回、新草稿照旧 insert。
- 小程序 harness：base 带上、merge、冲突页选择→重发→服务端一致。
- **真机门（交付前）**：broker 重部署 + 小程序重传；双端并发改**不同字段**（自动都保留）与**同字段**（弹冲突逐字段选）实测；`/code-review ultra`。

## 10. 分期

一次实现 Phase 1 + Phase 2，但落地/部署解耦：
- **Phase 1（办公端）**：§3 合并 + §4 链接去重 + §5 回写。办公端直连多维表，**不依赖 broker/小程序重部署**，可即测即上；回写时读当前+合并，已能防「回写冲掉手机改的其它字段」。
- **Phase 2（手机端）**：§6。补齐「手机保存也不冲掉办公端回写」，**须 broker 重部署 + 小程序重传**。

## 11. 已知取舍

- 「读-合并-写」非原子，读与写之间理论上有 TOCTOU 窗口；实际并发极低（同小团队、一份问卷通常一两人先后改），可接受；冲突弹窗的二次提交再校验 `theirs_mtime` 收敛绝大多数。
- 同字段冲突默认选中「你的值」，但要求用户显式确认每条（不静默）。
- `subjects`（一览表）不回写：估价师现场若采集了估价对象清单，本期仍在办公端录入、进报告，不进问卷字段（保持问卷=现场事实、报告=办公产物的边界）。
