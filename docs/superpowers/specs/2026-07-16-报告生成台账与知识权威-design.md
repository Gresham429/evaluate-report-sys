# 报告生成台账与知识权威 — 设计

- 日期：2026-07-16
- 状态：**已设计，待实施**
- 前置：[ADR-001 比较法算术移入 Python](../../decisions/2026-07-15-比较法算术移入-Python.md)、[表单输入与基础表版本管理决策记录](2026-07-16-表单输入与基础表版本管理-决策记录.md)
- 起点：main 分支，320 项测试全绿，v1.0.1 已交付 Windows exe

## 0. 用户的原话与它推出的三件事

> 「我希望你能给我做日志来帮助回溯，我们的系统里需要记录，这些可回溯的，包括基础表，
> 实例，模版等东西我们最后都会链接到钉钉进行维护，最后的希望公司每个估价师在自己
> 电脑上都能运行，所以会希望这些最后被统一维护，而不会因为离职交接或者别的情况导致丢失」
>
> 「如果基础表变动了需要提交申请，分为单独的这一份报告需要变动和整体的基础表需要更新」

这里面是**三件量级差很远的事**，不该塞进一个设计：

| | 事 | 本轮 |
|---|---|---|
| **A** | 报告生成台账：哪份报告用了哪版基础表、哪三条实例、什么指数、算出什么 | **做** |
| **B** | 知识资产的统一维护：基础表/实例/模板成为公司的，而非每台机器自己的 | 记下方向，不做 |
| **C** | 钉钉审批与同步 | 不碰，须贵司合规先行 |

**A 是 B 的前提**：连「这份报告用了什么」都没记，就无从验证同步有没有生效。
但 **A 单独交付不了「不丢失」**——见 §6。

## 1. 实测发现：基础表其实不是一张表

**这是 B 那一轮开工前必须先知道的事实，记在此处免得重新发现一遍。**

### 1.1 它长在每个项目的工作簿里

```
商业实勘表A.xlsx
  ├── 房地产实地查勘记录表          ← 项目A 的
  ├── 房地产比较法                  ← 项目A 的
  └── 比较因素条件说明表（基础表）   ← 公司的知识，却长在项目A 的文件里

商业实勘表B.xlsx
  └── 比较因素条件说明表（基础表）   ← 又一份拷贝
```

今天各份内容相同，是因为大家从同一个模板另存。**这是约定，不是机制。**

### 1.2 修正系数有两个入口

实测三份素材：基础表 I 列（修正系数）**都是公式**，指向比较法表的 X 列；X 列是手打的常数。

```
基础表 I3 = '=房地产比较法!X9'  → 值 2
比较法 X9 = 2                    ← 常数，系数的真身
基础表 I4 = 2                    ← 也有直接写死的，不统一
```

所以改系数有两个入口。这也意味着**「基础表」与「比较法表」并非独立**。

顺带：这让「改系数验指纹会变」这类测试不能直接改 I 列——openpyxl 存盘丢弃公式缓存值
（ADR-001 已实证），改完 28 个系数会全塌成 0，测试因无关原因变绿。须先 `data_only=True`
压平成值再改。

### 1.3 两个实测场景（2026-07-16）

```
场景一：同一份基础表，两个不同的商业项目（换报告编号、权利人、地址）
  商业A 指纹 df20ba03d3fb
  商业B 指纹 df20ba03d3fb   ← 相同
  → 第二次导入是空操作，库里仍是一版 ✓

场景二：有人把「重要场所距离」的系数从 2 改成 5
  商业C 指纹 a948d8c35ab2   ← 变了
  → 新版本入库，旧版原地不动 ✓
```

**指纹只看知识**（因素名、各档次描述与分值、修正系数、分值标尺），报告编号、权利人、
估价对象档次、选了哪三条实例一概不进。版本跟着知识走，不跟着项目走——这正是它该有的样子。

### 1.4 但场景二暴露了一个正在生效的隐患

估价师若认为「**这个**对象的临街状况系数该是 3 不是 2」，今天他唯一能做的就是改基础表：

```
他在自己项目的 Excel 里改 I3 → 导入
  → 成为本机「当前版」
  → 从此他机器上**所有新报告**都用新系数
  → 而他以为自己只调了这一单
```

**一次项目级的判断，静默变成了机器级的改动。** 系统还会夸他一句「已导入新版本」。

今天没有「单份偏离」这个概念，所以它必然被误表达成「全局改版」。这是 §5 的由来。

## 2. A 的设计：报告生成台账

### 2.1 存快照，不存引用

**已决策**：一条台账记录自己就能重算，不依赖任何别的东西还在不在。

理由：实例库是可变的（`InstanceStore.remove()` 存在，只是接口层没暴露——那是巧合，
不是保证）。存引用的话，有人事后动了实例库，台账就悬空，「能复现」退化成「希望没人改过」。

代价：每条约 10 KB。几百份报告几 MB，可忽略。

### 2.2 一条记录

```json
{
  "记录号": "a1b2c3d4e5f6",
  "报告编号": "正恒评报字[2026]第F071号",
  "生成时间": "2026-07-16T11:30:00",
  "经手人": "gresham@ZH-PC-03",
  "程序版本": "v1.0.1",
  "类别": "办公",

  "基础表": {
    "基线版本": "95d043e06567",
    "偏离": [],
    "实际知识": { "分值标尺": [...], "因素": [...] },
    "实际指纹": "95d043e06567"
  },

  "估价对象档次": { "临街状况": "四面临街", ... },
  "实例": [
    { "编号": "...", "位置": "...", "成交价": 2.52, "面积": ...,
      "交易情况指数": 100, "因素档次": {...},
      "市场状况指数": 98, "判断依据": "..." }
  ],
  "权重": [0.3333, 0.3333, 0.3333],

  "结果": { "比准价格": [2.92, 2.77, 2.80], "评估结果": 2.83, "离散度": 0.05 },
  "一览表": [ { "index": 1, "owner": "...", "area": 356.29, "unit_price": 2.83,
                "annual_value": 368030 } ]
}
```

要点：

- **基础表的知识整份存**，不只存指纹。把一条台账单独发给别人复核，他手上没有那个版本
  文件也能重算。
- **权重也存**。现在写死各 ⅓，但哪天开放可调，重算必须用当时那组，不能用今天的。
- **`基线版本` + `偏离` + `实际知识` 的三段形状**（§5）：今天 `偏离` 恒空、`实际指纹`
  与基线相同；将来加偏离功能，老记录的空数组语义天然正确，**不必重写历史台账**。
- **一览表也存**：单价可能被人工取整过（农用 1399.26 → 1400），那是估价师的判断，
  不存就复现不出报告上印的数。

### 2.2.1 `程序版本` 从哪来（实施前须先解决）

**今天代码里没有版本号这个东西**，且已经漂了：

```
pyproject.toml   version = "0.1.0"
git tag          v1.0.1
src/             无 __version__ 常量
```

台账记「哪个版本生成的」是为了「发现算法 bug 时能查出哪些报告受影响」——这要求版本号
**准确且唯一**，含糊的版本号比没有更坏。

**决定**：新增 `src/version.py` 的单一常量 `__version__`。

- 不用 `importlib.metadata` 读 pyproject：冻结的 exe 里包没被安装，读不到。
- 打包与 CI 都以它为准；CI 增加一步**校验 git tag 与 `__version__` 一致**，不一致即失败
  ——否则两者迟早各说各话，正如今天的 0.1.0 与 v1.0.1。
- 顺手把 `pyproject.toml` 的 `0.1.0` 对齐过来。

### 2.3 没重算就生成的报告，照样记

导入 Excel → 不重算 → 直接生成（第一轮那条老路）时，没有基础表版本、没有选实例。

**照记，并如实标明「未经系统重算，数值取自 Excel」。**

这不是缺失，恰恰是复核最想知道的事——**这份报告的数字不是引擎算的**。此时
`基础表`、`估价对象档次`、`实例`、`权重`、`结果` 均为 null，`一览表` 仍存。

### 2.4 只增不改

**没有删除接口，没有编辑接口。** 能被改写的记录不构成依据。

同一报告编号生成五次就是五条，各带时间戳。「最后那条」即交出去的那份，但中间改过什么
全留着。台账会有废条——这是台账该有的样子，不是缺陷。

### 2.5 存储

```
data/生成台账/
  20260716-113000-a1b2c3d4e5f6.json    ← 一条一个文件，文件名按时间可排序
```

一条一文件的理由同 `src/drafts/store.py`：只增不改天然适合，不必读改写整份，
写坏最多折损一条。文件名前缀用时间戳便于人肉浏览，记录号保唯一。

模块：`src/ledger/{model.py, store.py}`，风格对齐 `src/library/`、`src/drafts/`。
`LedgerStore` 只有 `append()` / `list_all()` / `get()`——**刻意没有 `remove()` 与 `save()`**。

### 2.6 照台账重算

因为 T3 已把引擎与 Excel、与存储解耦（`src/engine/inputs.py`），重放就是拿快照重新构造
输入，喂给同一个引擎：

```
台账快照 → ComparisonInput(类别, 实际知识, 档次) + Instance × 3 + 权重 → 引擎 → Result
```

**全程不碰实例库、不碰基础表库。**

需要对 `src/engine/compute.py` 做一处小重构：现在 `compute_from_selection(source, selections,
store)` 把「从库里取实例」和「算」揉在一起。拆成：

```python
def compute(source, instances, weights) -> Result          # 纯算
def compute_from_selection(source, selections, store)      # 取库 + 调 compute
```

重放走 `compute()`，跳过取库。

### 2.7 界面

新增「台账」页签：

- 列出每次生成：报告号 / 时间 / 经手人 / 基础表版本 / 评估结果 / 是否经引擎重算
- 点开看完整快照
- **「照此重算」按钮**：当场拿快照重算，把结果与台账里记的对比，显示一致或不一致

「照此重算」把「可复现」从承诺变成当场可验证的事实。这也是本设计里最便宜的一块——
引擎解耦之后几乎是白送的。

## 3. 顺带补的警告（§1.4 的便宜防线）

导入基础表时，若指纹与当前版不同，界面现在只说「已导入新版本 abc123」。改为说清楚：

```
⚠ 这与当前版 95d043e06567 不同。
  导入后，此机器上之后所有新建的报告都将使用新版。
  若你只是想调整某一份报告，这不是正确的做法——单份偏离尚未上线。
  旧版仍在，不会被删除。
```

**保留事实、判断交给人**——不阻止他导，但别让他以为自己只动了一单。

## 4. 测试

沿用本项目一贯的判据：**第一等的测试不是「能记」，是「记的东西真能把当时那个数算回来」。**

- `test_replay_reproduces_the_recorded_result`：拿台账快照重算，须得到与 `结果` 完全相同的数
- `test_replay_survives_a_wrecked_library`：**把实例库整个删掉，重放照样算得出**
  ——这条才是「快照自洽」的证明，其余都是陪衬
- `test_ledger_is_append_only`：同一报告编号生成五次 → 五条，一条不少
- `test_report_without_recompute_is_recorded_as_such`：老路生成的报告，`结果` 为 null
  且标明未经重算
- `test_deviation_field_shape_is_forward_compatible`：`偏离` 恒空数组，`实际指纹` == 基线
- 金样：办公 2.83 / 农用 1399.26 / 商业 3.32 走完整链路后，台账重放仍得同一个数

## 5. B 的方向（本轮不做，记下来）

用户要的两条路，技术上是不同的东西：

```
整体更新（公司级）
  改基础表 → 钉钉提申请 → 批准 → 成为公司当前版 v(N+1) → 各机器同步
  之后所有新报告用 v(N+1)；旧报告台账仍指向 vN，照样能复现

单份偏离（项目级）
  「这个对象的某因素系数该不一样」→ 钉钉提申请（附理由）→ 批准
  → 只对这一份报告生效
  → 台账记：基线 vN + 偏离清单 + 审批单号 + 理由
  → 公司当前版纹丝不动，别人不受影响
```

**关键原则：偏离必须存成「基线版本 + 差异」，不能存成「另一个版本」。**

否则一年下来库里躺着两百个指纹，分不出哪些是「公司知识演进」、哪些是「某个项目破了个
例」——版本号会失去意义。§2.2 的三段形状就是为此预留的。

**B 的核心不是「同步文件」，是先要有一个「权威源」。** 今天系统能认出「这两份基础表不
一样」（指纹），但认出来之后**没有任何机制说哪份是对的**。

### 一个现在就能做的体检

指纹已经让「不一样」变得可检测。拿全公司的历史 Excel 跑一遍指纹，就能看出到底有几个
基础表变种在流通。这在有统一维护之前就有用，且几乎零成本。

## 6. 诚实的边界

**台账解决「可回溯」，不解决「不丢失」。**

`data/生成台账/` 与实例库、基础表在同一个目录里。张三离职，他机器上的台账连同实例库一起
没。台账让你能回答「这份报告当时用了什么」，**前提是你还拿得到他那台机器**。

「不因离职丢失」要靠 B——把 `data/` 从「每台机器自己的」变成「公司的」。A 是 B 的前提，
但 A 单独交付不了这个承诺。

**钉钉的边界**：审批流是钉钉的强项，权威源是我们的责任。钉钉负责「谁批准了什么」，
我们负责「批准的东西如何被准确地用上、并被记下来」。这条边界现在划清，将来接的时候不会糊。

## 7. 不做的

- **删除/编辑台账** —— 只增不改
- **台账同步到别的机器** —— B
- **单份偏离的功能本身** —— 只留数据形状与警告（用户决定）
- **钉钉** —— C，须合规先行
- **报告里写明用了哪三条实例** —— 牵涉执业规范，须执业估价师定夺（决策记录 §8.5）
- **权重可调** —— 写死各 ⅓（用户决定）
