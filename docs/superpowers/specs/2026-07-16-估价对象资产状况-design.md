# 估价对象资产状况（逐因素文字依据 + 档次）— 设计

- 日期：2026-07-16
- 状态：设计已获用户认可，待落实现计划
- 触及：`model.py`、`engine/knowledge.py`、`extractor/`、`library/importer.py`、
  `web/app.py`、`web/static/index.html`、`renderer/render.py`、`tools/build_templates.py`、
  `ledger/`、`validator/`

## 0. 用户的原话与它推出的三件事

> 「实地勘察表记录表，资产状况要求先写文字内容作为依据，然后点选估价对象因素档次，
> 最后的报告里估价对象资产状况的内容要求具体到文字内容，这些都是灵活变动的（也就是说
> 实地勘察表绝大部分都需要我们自己手写的，还有的就是根据手写的内容进行选择）。」

推出三件事：

1. **逐因素有一段手写的「描述」**，是选档次的依据（灵活变动、绝大部分手写）。
2. **档次是「根据手写内容进行选择」**——先有描述，再点档次。
3. **报告里的资产状况要「具体到文字内容」**——出现的是那段手写描述，不是档次标签。

## 1. 实测发现：现状与三份真文件的结构

### 1.1 报告的资产状况段现在带的是金样死文字

报告（三）估价对象资产状况 = **三张 3 列表**〔组 | 因素 | 描述〕，逐因素一行：

```
区位状况 | 楼层     | 所在层数为第十二层和第十五层。
实物状况 | 建筑结构 | 钢混结构，地上23层，地下3层。
权益状况 | 使用限制 | 无不利使用限制
```

这三张表现在**没有占位符**（office 模板里 0 个 `{{ }}`，唯一例外是 `建筑规模` 已接
`{{ subjects_narrative }}`）。即：现在每份 office 报告都原样带出**办公金样那份**的逐因素
描述。这正是本次要补的洞。

### 1.2 实勘表逐因素结构：A=组、B/C=因素、D=描述、E=档次

`办公实勘表、比较法.xlsx` 的第一张 sheet「办公房地产实地查勘记录表」就是用户说的实勘表：

```
r17 A=资产状况
r18 A=区位状况  B=重要场所距离  D=距离北干街道直线距离约1.5公里…  E=距区域中心距离1-1.5KM
r33 A=实物状况  B=建筑规模      D=…356.29 平方…               E=适中
r42 A=权益状况(二) B=维修费用承担 D=出租人承担。                 E=出租人承担
```

- **D 列 = 逐因素手写描述**（依据）
- **E 列 = 据此点的档次**
- **A 列 = 三组的分节标记**（区位/实物/权益），每组头一行出现一次

报告三张表的「描述」列 = 实勘表 D 列，一一对应。

### 1.3 分组是知识，长在实勘表里，不长在基础表里

- 基础表 sheet「比较因素条件说明表（基础表）」给的是因素名 + 档次选项 + 系数，
  它的 B 列只有**更细的子组**（位置/交通/配套/环境）盖住区位那段，**没有区位/实物/权益
  这层三分**。
- 三分只在**实勘表 sheet 的 A 列**。三类样本都验过一致：`区位状况`@r18、`实物状况`@r33、
  `权益状况`@r42（办公写成「权益状况(二)」，故按前缀匹配）。sheet 名农用/商业是
  「房地产实地查勘记录表」、办公是「办公房地产实地查勘记录表」，故按关键字「查勘记录表」
  匹配。

结论：**因素→组** 的映射从实勘表 sheet 读，系统不替估价师判断谁属区位谁属实物（铁律 8）。

### 1.4 资产状况是「每报告一份」，不是「每估价对象一份」

三份模板里 `资产状况` 均只出现 1 次；办公 2 个估价对象也共享同一段资产状况。故资产状况
描述挂在项目层（每报告一份），不挂在单个估价对象上。

## 2. 设计（逐层）

数据流一句话：`基础表知识(因素+分组+档次选项)` → 表单按组逐因素填〔描述 + 档次〕→
档次进引擎算 `系数→单价`（不变）；描述随项目进报告三张表（新）+ 进台账快照。

### 2.1 数据模型（`model.py`）

描述是「报告数据」，组好后冻进 `Project`，让 `render()` 只管循环、不认识基础表：

```python
@dataclass(frozen=True)
class ConditionFactor:
    name: str            # 楼层
    description: str     # 所在层数为第十二层和第十五层。（手写）

@dataclass(frozen=True)
class ConditionGroup:
    name: str            # 区位状况 / 实物状况 / 权益状况
    factors: tuple[ConditionFactor, ...]

# Project 新增字段：
asset_condition_groups: tuple[ConditionGroup, ...]
```

分组与因素次序在 web 层用基础表知识组好，连同各因素的手写描述装成上面的结构，冻进
`Project`。这样 `Project` 自包含、可直接渲染、可整份进台账快照。

### 2.2 基础表知识加「分组」（`engine/knowledge.py`）

- `Factor` 增一个 `group: str`（区位状况/实物状况/权益状况）。
- 来源：导基础表那本 workbook 里的**实勘表 sheet A 列**分节标记，按因素名把基础表的因素
  归到三组。导基础表时顺带读一次（同一本 workbook，不额外要文件）。
- **不进指纹**：分组是呈现用元数据，**不掺进算术指纹**（指纹仍只认系数/档次/分值）。
  于是三个基础表金样指纹**一个都不变**，`tests/` 里锁死的指纹不用改。
- 旧基础表没分组：**不崩**。退化成不分组（单一「资产状况」组）+ 提示「重导基础表以获得
  分组」。交付前重导一次即可。
- 因素名对齐：基础表 B/C 两列名（C 因素名优先、退 B），与实勘表 B 列因素名按归一化字符串
  匹配；对不上的因素 → 不分组 + 记一条 warning，不静默吞。

### 2.3 提取器：实勘表描述可导入预填（`extractor/` + `library/importer.py`）

- 现有导入已预填 19 字段 + 一览表 + 28 档次（档次来自比较法 sheet D 列）。
- 这里加读**实勘表 sheet D 列**的逐因素描述（按 B 列因素名 + A 列组），预填进表单。
- 手写仍是主路；导入只是「有旧实勘表就不用重敲」。

### 2.4 表单（`web/static/index.html`）

- 七步向导里资产状况段，按三组（区位/实物/权益）铺开；每因素一行：**描述 textarea 在前 →
  档次下拉在后**，落实「先写依据、再点档次」。
- 档次下拉复用现有 `/api/factors` 的选项；描述是新输入。
- 草稿自动存把描述一并存下（沿用 `openForm()` 收口 + 自动存那套；铁律见坑 §5.2）。

### 2.5 引擎边界（不动）

- 引擎只吃档次 → 系数 → 单价。**描述一个字都不进 `compute()`**。
- 同一输入同一输出、12 个金样数字照旧复现（铁律 1/2/3）。这条要有测试正面证明（§3）。

### 2.6 渲染 + 模板（`renderer/render.py` + `tools/build_templates.py`）

- 三张资产状况表改成**按因素循环**（同一览表 `tools/table_loop.py` 的既有做法）：
  模板每组留一个循环行
  `{% for f in 区位因素 %}| {{ f.name }} | {{ f.description }} |{% endfor %}`。
- 组标签单元格（区位状况，跨行合并）照原样保留。
- `build_templates.py` 加一步专门参数化这三张表（定位三张表 → factor 行换成循环行）。
- `render.build_context()` 从 `project.asset_condition_groups` 摊出
  `区位因素/实物因素/权益因素` 三个列表供模板循环。
- **行序**：因素按基础表行序（`knowledge` 已「因素按基础表行序排列」），组内顺序即随之定；
  须与金样三张表的行序一致，由 §3 金样复现钉死。基础表里的表头/表尾（如「级别」「修正系数」）
  本就不在因素集中，不会漏进循环。

### 2.7 台账（`ledger/`）

- 快照把 `asset_condition_groups` 一起存（「照此重算」能复现同一份报告正文；铁律 6「存当时
  那份」）。
- 新增字段、**只增不改**；旧台账无此字段即 `None`。描述不参与 replay 的数字校验，故对既有
  replay 复现无影响。

### 2.8 校验（`validator/`）

- 某因素描述留空 → 只提示不拦。
- 描述填了却没点档次（或反之）→ 提示。
- 沿用「校验只提示不阻断」（铁律 7）。

## 3. 测试

- **金样复现（关键）**：用金样自己的实勘表描述渲染，三张资产状况表须与金样原文逐字一致。
  现在是死文字、复现是白送的；改成循环后必须仍一模一样——这条测试是本设计不砸金样的证据。
- **分组正确**：三类基础表导入后，区位/实物/权益 归组与实勘表 A 列一致。
- **指纹不变**：三个基础表金样指纹原样（证明分组没掺进指纹）。
- **导入预填**：实勘表 xlsx 能把逐因素描述填进表单结构。
- **引擎不受影响**：12 个数字照旧（现有 `test_engine_golden.py` 不动即绿）。
- **草稿往返**：描述随草稿存取、`openForm` 切换不串。

## 4. 范围与风险（先说清）

- 改动**触碰渲染路径**（贴近金样铁律），但只碰资产状况三张表、不碰算术；金样复现测试兜底。
- 最费手的是 §2.6 的**合并组标签单元格 + 循环**：`table_loop.py` 有先例，但这三张表结构
  与一览表略不同，需小心 docx 合并单元格。
- 一个完整多任务特性（约 6–7 个实现任务），一个 spec 一个实现计划走得完，不拆子项目。

## 5. 诚实的边界 / 本轮不做的

- **不新造措辞**：系统只搬运手写描述，不替估价师生成/润色资产状况文字（铁律 7「不替他填」）。
- **不改因素三分的判定**：谁属区位/实物/权益，认实勘表 A 列，系统不自行归类。
- **报告里档次是否单列**：档次驱动比较法表的系数，资产状况三张表只显示描述、不显示档次
  （与金样一致）。若将来要在报告别处列出档次，另议。
- **权重/方法**：本设计不碰，沿用现状（写死各 ⅓ / 单一方法）。
