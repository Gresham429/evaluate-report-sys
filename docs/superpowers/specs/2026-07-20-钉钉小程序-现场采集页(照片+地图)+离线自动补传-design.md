# 设计：钉钉小程序 · 现场采集页（照片+地图智能预填）+ 离线自动补传（v2 起步）

- 日期：2026-07-20
- 状态：**用户已定方向并「开始做吧」**——三项决策已敲定（见 §0）；本设计写完即实现+自测。
- 承接：`2026-07-19-钉钉小程序前端-design.md`（v1）、`2026-07-20-钉钉小程序前端-本地缓存优化-design.md`（v1.1.1 缓存）、`serverless/survey_broker/`（已上线 broker）。

## 0. 用户已定的三项决策

1. **照片存储＝钉钉多维表附件字段**。落地解读：photos 现契约是 `content.photos: string[]`（URL 列表，`record.py CONTENT_KEYS`、`backend.py:77`、`model.py:54` 三处钉死）。故 broker 把照片字节上传到钉钉获得**可下载 URL**，仍以 URL 串写进 `content.photos`——**办公端零改动**（不新增列、不动契约测试）。真正的钉钉媒体/附件上传接口形状**待真机校准**（同 whoami/prefillGeo 的既有校准法）。
2. **新建独立「现场采集」页**（`pages/capture/`），拍照 + 定位预填合一，从表单页跳入；**地图智能预填从表单页移到此页**。
3. **离线自动补传一起做**：无网时暂存/提交/拍照都落本机不丢；联网后**自动补传**（网络恢复事件 + 进页/回前台触发），无需手点。

## 1. 范围

**做（P0）**
- G1 现场采集页：拍照（多张、可删、缩略图）+ GPS 定位 + 地图预填地理事实（移自表单）。
- G2 照片上传：小程序压缩→base64→broker `uploadPhoto`→钉钉媒体上传得 URL→写入 `content.photos`。**broker JSON-only 架构不变**（base64 进 JSON，不引 multipart）。
- G3 离线自动补传：本地待同步队列（草稿内容 + 待上传照片 + 待提交标记）；联网自动 flush（重试幂等）。

**非目标（延后）**
- 28 因素档次 / 逐因素描述（v2 下一步，须估价师定因素清单）。
- 照片存成多维表**独立附件列**（本版走 URL-in-JSON，办公端零改；将来若要缩略图列再加列+改契约）。
- 跨设备续填（仍 v2）。

## 2. 架构与数据流

```
现场采集页(capture)
  拍照: dd.chooseImage → dd.compressImage → 读 base64(# 待真机校准 文件读取API)
        → 先入本地待上传队列(缩略图即时显示,不丢) → 联网则 broker uploadPhoto → 得 url → 落 content.photos
  定位: dd.getLocation → gps；地图: broker prefillGeo → 显示地理事实(只读参考,同 v1)
  返回表单: 采集结果(photos/gps/geo)随本地草稿缓存带回,表单提交时一并 saveDraft
broker(FC, JSON-only)
  新增 action uploadPhoto: {name, dataBase64, mime?} → DingtalkMedia.upload() → {url}
  saveDraft/submit/loadDraft/prefillGeo/whoami 不变
离线自动补传(sync)
  网络恢复/进页 → 遍历本地 dirty 草稿 → 补传待上传照片 → saveDraft → (若待提交)submit → 标同步
```

- **photos 契约不变**：`content.photos: string[]`（URL）。本地另存**只在本机**的 `pendingPhotos:[{localPath,name}]`（未上传成功的），上传成功即转成 URL 进 `content.photos`，从 pendingPhotos 移除。服务端永远只见 URL。

## 3. broker 改动（新增一个 action + 一个协作者，镜像 amap/identity）

- `serverless/survey_broker/media.py`（新）：`DingtalkMedia`，`upload(name, data: bytes, mime) -> {"url": ...}`。
  - token 复用同应用 `NotableClient.access_token`（同 identity）；transport 可注入，单测零网络。
  - 真钉钉媒体/附件上传端点 `_URL` + 响应解析 **`# 待真机校准`**（候选：钉钉存储/媒体上传接口；上传得 mediaId/downloadUrl，取可下载 URL）。失败→ValueError（映射 4xx）。
- `handler.py`：`dispatch(..., media: _Media)` 增 `uploadPhoto` 路由；`_Media` Protocol；`handler()` 构造 `DingtalkMedia`。
- `server.py`：`build_context`/`handle`/`_make_handler`/`main` 全程带 media。
- `package.py`：`FILES` 补 `media.py`（否则打包漏文件）。
- **base64 体积**：客户端先 `dd.compressImage`；FC 请求体上限（默认较小）→ 单张压到合理尺寸；`# 待真机校准` 体积上限。
- 测试：`tests/test_survey_broker_media.py`（FakeTransport 3 例）+ `test_survey_broker_handler.py` 补 `FakeMedia` + uploadPhoto 路由；`test_survey_broker_server.py` 补 media 端到端。**契约测试 `test_survey_broker_record.py` 不受影响**（photos 契约没动）。

## 4. 小程序改动

- `app.json`：注册 `pages/capture/capture`。
- `pages/capture/`（新，capture.axml/js/acss/json）：
  - 入参 `?draftId=<localId>`：从本地草稿缓存载入已拍照片/gps/geo。
  - 拍照区：`dd.chooseImage(count)` → 压缩 → 缩略图网格 + 删除；每张先入 `pendingPhotos`（本地不丢），联网即 `uploadPhoto`→URL 进 `photos`。
  - 定位+地图卡：`dd.getLocation`→gps；`prefillGeo`→地理事实（**移自 form.axml 的地图卡**）。
  - 「完成」→ 写本地草稿缓存（含 photos/pendingPhotos/gps/geo，标 dirty）→ `navigateBack` 回表单。
- `pages/form/`：删地图卡（移走）；加「现场采集（拍照/定位）」按钮 → `navigateTo capture?draftId=<localId>`；`_content()` 的 `photos` 改从缓存读（采集页写入）。
- `utils/store.js`：草稿对象加 `photos:[]`、`pendingPhotos:[]`、`pendingSubmit:bool`；新增 `listDirty()`（索引 dirty 条）。
- `utils/sync.js`（新）：`flush(broker, store)` → 遍历 dirty 草稿 → 逐张 `uploadPhoto(pendingPhotos)`→转 photos → `saveDraft` → 若 `pendingSubmit` 再 `submit` → 成功标 synced/submitted。全程幂等（saveDraft 按 survey_id upsert、submit 幂等、照片上传成功即出队去重）。
- `app.js`：`onLaunch` 注册 `dd.onNetworkStatusChange`→有网即 `sync.flush`；`index`/`capture` `onShow` 也触发一次 flush（双保险）。
- 触发链闭环：v1.1.1 的「断网暂存/提交不丢、标未同步」保持；本版把「联网后**手动**重试」升级为「**自动** flush」。

## 5. 关键流程

**离线拍照→回家联网**：现场无网拍 3 张→压缩→`pendingPhotos` 本地存、缩略图即显；点完成回表单点提交→saveDraft 失败（无网）→草稿 dirty+pendingSubmit 本地留。回家 WiFi→`onNetworkStatusChange` 触发 `flush`→逐张 uploadPhoto 得 URL→saveDraft（带 photos）→submit→标已提交、清重内容。**全程零丢、零手点。**

**幂等/中断恢复**：flush 任一步失败即停在该草稿（保持 dirty），下次触发重跑；saveDraft 同 survey_id 覆盖、submit 重复无害、已上传照片已出 pendingPhotos 不重传。

## 6. 一致性与边界

- 照片上传部分成功：成功的转入 photos、失败的留 pendingPhotos，dirty 保持；不阻塞其余字段暂存。
- FC 体积/超时：单张压缩 + 逐张上传（非一次性打包）；`# 待真机校准` 单张上限与并发。
- 隐私/#9：照片经 broker 进公司受控钉钉存储；提交成功清本机重内容（含缩略图缓存）。
- flush 并发：加一个内存 `flushing` 锁，避免 onShow 与网络事件同时触发重入。

## 7. 铁律处置

- #1 金样 / #3 运行时零 AI：仍只采集、不算术；照片/地图是确定性采集与检索。
- #7/#8：地图只给地理事实（只读），档次/判断不在本版。
- #9（钉钉改写版）：照片留公司受控钉钉；本机提交后即清。

## 10. 追加需求（2026-07-20 用户）：标签对齐 + 逐因素数据源

**10.1 基本字段标签与实勘表逐字一致（已实现）**
实测 7 份实勘表左列标签：19 项中 16 项**全类别一致**，改后与表格逐字同（住址/法定代表人或负责人/实地勘查日期/委托人提供的材料/是否取得产权证书/地址/现使用状况/评估报告编号/估价报告出具日期…）。
3 项逐类别微差：`scale`＝「估价对象规模」（5/7），办公/商业＝「规模」→ `LABEL_OVERRIDES` 逐类别覆盖。
`issue_date/work_period`：工业/建设用地 xlsx 的 F3/F4 标签互换（**已知 Excel 笔误**，见项目记忆；代码按单元格位置取值），故**统一用规范标签**，不照抄笔误——这是与「完全一致」的一处刻意偏离，已在 form.js 注明，待用户回修 Excel 后可去偏离。
落地：`form.js` FIELDS 全量更新 + `LABEL_OVERRIDES` + `fieldsFor(category)`（选类别/续填时按类别重算标签）。

**10.2 逐因素清单＝按类别取自实勘表（数据已就位）**
用户明确「因素清单已在每个 xlsx、类别不同」。实测每类别 27–28 因素，分 区位状况/实物状况/权益状况 三组，逐类别不同（如农用有「有机质含量/灌溉条件」，停车场有「停车进出便利度/地面硬化」，办公有「智能化程度」）。每因素在表里带 **描述(D列)+档次(E列)**。
落地数据源：`tools/gen_survey_factors.py`（从 7 xlsx 抽取，可重跑）→ 生成 `miniprogram/factors.js`（`{类别: [{section, items:[因素名]}]}`）。**逐因素采集 UI（描述+档次 → 落 content.asset_conditions/subject_levels）属下一步实现**，本轮先备数据源。
