# 比较法引擎与实例库 — 设计文档

- 日期：2026-07-16
- 状态：待评审
- 前置决策：[ADR-001 比较法算术移入 Python](../../decisions/2026-07-15-比较法算术移入-Python.md)

## 1. 目标

支持**动态选择比较法实例**：维护一个实例库，生成报告时由估价师挑选三条，系统据此重算评估结果。

## 2. 范围与拆分

用户一次提出四项需求，量级差异极大，**必须拆开做**，各自出设计、各自验收。

| | 内容 | 依赖 | 本轮 |
|---|---|---|---|
| ① | 比较法引擎 | 无 —— 地基 | ✅ |
| ② | 实例库 | ① | ✅ |
| ③ | 全中文界面 | 无 | ✅ |
| ④ | 钉钉集成 | ① | ❌ 单独立项 |

**钉钉不在本轮**，原因不是技术，是业务：它要求局域网机器出外网、估价数据经第三方云，须贵司合规先行。用户已同意单独立项。

## 3. 铁律改写

**旧 C1**：Excel 的公式是既定正确的，系统只读不算。

**新 C1**：
- Excel **基础表的知识**（因素、档次、系数、分值）是既定正确的，系统只读不改
- **比较法的算术由系统执行**，且必须精确复现三份金样的 12 个数字
- **实勘表的取值语义仍严格只读**（原 C1 在此处不变）

理由与实证见 ADR-001。核心：`openpyxl` 写回 Excel 会清空其全部缓存结果（实测 T37/T39 → None），"软件改 Excel 再读"这条路不通。

### 3.1 Excel 的两个角色，寿命不同

| 角色 | 内容 | 寿命 |
|---|---|---|
| **知识源** | 基础表：因素、档次、系数、分值 | **长期**。估价师持续维护，改 Excel 即生效 |
| **数据源** | 实勘表：项目与估价对象数据 | **过渡**。用户规划中将由钉钉表单/结构化文档取代 |

架构须把「数据从哪来」抽象为接口，Excel 只是当前的一个实现。否则接钉钉时要动筋骨。

## 4. 比较法引擎

### 4.1 为什么不能直接跑 Excel 公式（已实证否决）

尝试 `formulas` 1.3.4 加载办公表求值，结果：

```
M 列（因素指数）  只求出行 2-8，行 9-36 全部缺失
T 列（比准价格）  只求出 2-8、38，T37/T39 缺失（依赖 M9:M36）
```

**卡在核心公式的整行引用上**：

```
=(INDEX('基础表'!$31:$31, MATCH(TRIM(E9),'基础表'!3:3,0)) − INDEX(…)) × '基础表'!$I3 + 100
                ↑ 整行引用                    ↑ 整行引用
```

该库对 INDEX 内的整行引用**静默跳过**——不报错，结果里就是没有。若不逐格核对会误以为成功。另外它也在办公表的外部引用 `[C:\Users\admin\Desktop\…]现场勘查人'!B:C` 上报错。

**结论：Excel 公式解释这条路否决，有实证。不承诺"自动提取任意 Excel 公式"。**

### 4.2 三份表的现状（实测）

| | 指数公式 | 比准价格 | 评估结果 | 因素数 |
|---|---|---|---|---|
| 农用 | 同形 | 30 项连乘 | `ROUND(T37*T38+U37*U38+V37*V38,2)` | **27** |
| 办公 | 同形 | 30 项连乘 | 同 | **28** |
| 商业 | 同形 | 30 项连乘 | 同 | **28** |

**一套公式形态 + 三张规模不同的知识表**。30 项 = 2（交易情况 + 交易日期）+ 28（因素槽位）；农用 27 个因素，余下槽位空置。

报告正文自述「估价方法通常有比较法、成本法、价值折算法、剩余法**四种**」——将来的新方法可能形态完全不同。

### 4.3 分层：什么是知识，什么是算术

```
从 Excel 提取（知识，会变）          写进策略（算术，随方法版本固定）
──────────────────────────        ─────────────────────────────
28 个因素是哪些                     因素指数 = (实例分−对象分)×系数+基准
每因素 5 档怎么描述                  比准价格 = 成交价 × ∏(基准/指数)
每差 1 档的修正系数                  评估结果 = Σ(比准价×权重)
分值标尺 2/1/0/-1/-2                离散度   = MAX/MIN − 1
```

**用户改系数、改档次、加因素 → 改 Excel 基础表即生效，代码一行不动。**

### 4.4 公式显式化：`knowledge/比较法-市场比较法-2026版.yaml`

公式**不散落在代码里**，完整、显式、带版本地写出来：

```yaml
方法: 市场比较法
版本: 2026-07
适用类别: [农用, 办公, 商业]
基准值: 100

公式:
  因素指数: (实例档次分 − 估价对象档次分) × 每差1档系数 + 基准值
  比准价格: 成交价 × (基准值/交易情况指数) × (市场状况指数/基准值) × ∏(基准值/因素指数)
  评估结果: Σ(比准价格 × 权重)
  离散度:   MAX(比准价格) / MIN(比准价格) − 基准值/100

知识表来源:
  工作表: 比较因素条件说明表（基础表）
  因素行: 3..30        # 按实际非空行数取，农用 27、办公商业 28
  档次列: D..H
  分值行: 31
  系数列: I

对照基准:              # 验收锁死，算歪即红
  农用: {比准价格: [1410, 1393.89, 1393.89], 评估结果: 1399.26}
  办公: {比准价格: [2.92, 2.77, 2.80],       评估结果: 2.83}
  商业: {比准价格: [3.15, 3.40, 3.40],       评估结果: 3.32}
```

YAML 是**权威表述与文档**，供估价师阅读核对；策略实现须与之逐条对应。

### 4.5 策略：新比较法 = 新策略文件

```
src/engine/
├── __init__.py          # 工厂 & 注册表
├── spec.py              # 读 knowledge/*.yaml
├── knowledge.py         # 从 Excel 基础表提取因素/档次/系数/分值
└── methods/
    ├── base.py                  # 抽象基类：ComparisonMethod
    └── market_2026.py           # 市场比较法-2026版（首个实现）
```

新比较法（成本法/收益法/新版比较法）→ 新增 `methods/xxx.py` + 对应 YAML，**注册即可用，老策略不动**。

**诚实的边界**：新方法若形态不同，须写代码。这是无法回避的——不同的算法就是不同的算法。但它被隔离成一个命名、带版本、可独立测试的单元，而非改动既有代码。

## 6. 实例库

### 6.1 数据模型

```python
@dataclass(frozen=True)
class 实例:
    编号: str              # 类别-起始年(月)-位置
    类别: Category
    位置: str
    成交价: float
    面积: float
    出租用途: str
    交易情况: str          # 如「正常」
    租期原文: str          # 原样保留，如 '2025-2026'
    起始日: date | None    # 解析所得；只有年份时为该年 1 月 1 日
    日期精度: 精度          # 完整 / 仅年月 / 仅年
    因素档次: dict[str, str]   # 28 项：因素名 → 档次描述
    备注: str = ""         # 选填
```

**`市场状况指数` 不在库内** —— 它是「实例 × 本项目价值时点」的配对属性，同一实例用于不同时点的项目必须重填。每次选完实例由估价师现填，**系统不推算、不给默认值**。

### 6.2 分类、排序、编号

- **分类**：农用 / 办公 / 商业
- **排序**：按起始日期，从新到旧
- **编号**：`类别-起始年(月)-位置`，如 `办公-2026-01-兴耀科创城A幢09层`；日期仅有年份时退化为 `农用-2025-白浪村围垦五工段`

### 6.3 日期精度分级（用户选定方案丙）

「交易日期」在现有素材中是自由文本，**实测四种格式并存**：

```
办公 A   '2026.1.15-2026.7.14'      完整
商业 A   datetime(2025, 10, 28)     真日期类型，非区间
农用 A   '2025.7-2026.7'            仅年月
农用 B/C '2025-2026'                仅年份
```

**做法**：有什么记什么，原文保留，**日期不精确的打标记**，选用时提示。不拦截、不强制补全。

**理由**：强制补全会当场卡住——那 2 条的真实租期多半已查不回；照单全收则让"日期不可靠"这个事实在库里消失。丙保留事实，把判断交给人。

**佐证**：农用三条实例的市场状况指数**全填 100**（不调整），而办公为 98/95/95。合理推测——日期含糊到只剩「2025-2026」，估价师无从判断市场涨跌，只好放弃调整。该实例入库后，那个 100 会被后人继承却无人知其来由。标记能把这个真相留住。

### 6.4 不做的事

**不做推荐、不高亮、不打分、不筛选。**

曾从三份金样反推出一条规律——起始日距价值时点越近，市场状况指数越接近 100（实测 A:70天→98、C:261天→95、B:298天→95）。看似成立，但**用户明确表示自己不掌握这套专业逻辑**，双方均无法验证它是否为真实的估价准则。三个样本反推的规律不足以固化为系统推荐：真实估价中位置相似度、面积可比性可能比时间更重要。

**在专业场景里，一个无人能验证的推荐比没有推荐更危险**——它误导使用者，而责任落在签字的估价师身上。

若日后要做，前提是由执业估价师确认可比性的优先维度，而非从样本反推。

### 6.5 存储

`data/实例库.json`，UTF-8，人类可读可手改。理由：单机单用户、数据量小（预计数百条）、无并发；JSON 便于估价师直接查看与备份，无需引入 SQLite 的运维负担。

### 6.6 批量导入

源为**现有实勘表 Excel**（用户确认）。实测可从三份素材抽出 **9 条**实例（每份 3 条），其中 7 条日期可解析、2 条仅有年份。

导入流程：选 Excel → 抽取 → 列出待入库清单（含日期精度标记）→ 估价师确认 → 入库。重复编号时提示，不静默覆盖。

## 8. 测试

### 8.1 引擎验收（最高优先级）

三份金样的 **12 个数字必须精确复现**：农用 `1410/1393.89/1393.89→1399.26`、办公 `2.92/2.77/2.80→2.83`、商业 `3.15/3.40/3.40→3.32`。可行性已验证（约 40 行原型全部命中）。

### 8.2 防漂移

引擎结果须与 Excel 缓存值一致。这是双实现漂移的唯一防线——一旦估价师改了基础表而未同步，测试会因金样对不上而红。

### 8.3 实例库

- 9 条素材实例导入后编号、排序、日期精度标记正确
- 仅有年份的实例（`2025-2026`）被标记为「仅年」且编号退化到年
- 换实例后评估结果随之改变（对照手工计算）
- 市场状况指数未填时不得进入下一步

## 9. 已知风险

| 项 | 说明 | 处置 |
|---|---|---|
| 双实现漂移 | 估价师改基础表**公式**不再生效（只有改**数据**生效） | 用户文档显著说明；金样回归测试兜底 |
| 新方法须写代码 | 形态不同的方法无法参数化 | 隔离为命名策略，老策略不动 |
| 日期精度参差 | 9 条素材中 2 条仅有年份 | 标记 + 提示，不强制 |
| 市场状况指数无依据留存 | 现有 98/95/95 全无理由记录 | 新增选填备注字段沉淀 |

## 10. 权重

比较法末步 `评估结果 = Σ(比准价格 × 权重)`。三份表**全部为各 ⅓**（实测 T38/U38/V38 = 0.333333333333333，合计 1.0），即三个实例等权、简单平均。

**设计（用户确认）：写死各 ⅓，本轮不做可调。** 待用户提出需求再议。

**这个决定顺带堵住了一个可追溯性漏洞。** 实测：三份报告正文中，「权重」与「加权」二词出现次数**均为 0** —— 权重取值完全不在报告中披露。等权时无所谓（等权即简单平均，无裁量空间）；但若允许调整，估价师把权重改为 0.6/0.2/0.2 会让评估结果由 2.83 变成 2.86，**而报告里没有任何地方体现这一调整**，审核人无从得知结论如何得出。不做可调 = 不存在这个洞。

**日后若要开放可调，须一并解决**：权重取值与理由如何进入报告正文，而非仅存于系统内。否则会制造一个「可以悄悄影响结论、且查不出来」的口子。
