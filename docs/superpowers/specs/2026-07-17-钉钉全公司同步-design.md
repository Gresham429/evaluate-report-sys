# 设计：钉钉全公司同步（知识/台账/报告托管 + 统一编号）

- 日期：2026-07-17
- 状态：架构决策已与用户（建设方）逐条敲定（本文 §3 的 ①~⑥）；**仅设计，未写代码**
  —— Store 后端须等钉钉承载层/接口确定后才能实现。
- 定位：这是一份**对接设计依据**，给做钉钉集成的人（你们 IT / 钉钉侧 + 后续本仓改造）看。
- 关联：承接 docs/README §7「C：钉钉审批与同步」「B：知识资产统一维护」「报告编号可领取」。

## 0. 一句话

把系统从"单机、数据留本机"改成"**钉钉为权威 + 本地拉取缓存 + 改动回写**"：知识（基础表/实例/模板）、
台账、成品报告都汇到公司钉钉，报告编号全公司统一。**断网仍能读缓存、出草稿；出正式报告需联网**。

## 1. 背景与目标

- 现状：单机离线，数据在本地 `data/`（实例库/基础表/草稿/台账）。知识随人走、编号各机各编、
  报告散落——公司层面无统一底账。
- 目标（一期）：知识与记录**归公司、不因离职丢失**、**报告编号全公司统一**、台账成为**可审计的公司底账**。
- 非目标（一期）：审批流、权限细分、通知统计（→ 二期）；移动端智能问卷（→ 专项，见 §7）；
  附件管理与渲染编排规范（用户 2026-07-17 明确往后放）。

## 2. 总模型

```
钉钉（企业团队，权威）  ── 拉取缓存 ─▶  本地（缓存 + 出报告）
        ▲                                   │
        └──────── 改动回写（append/发布）─────┘
```

- **钉钉 = 权威源**（company-controlled，非第三方——这是 #9 得以放宽的前提）。
- **本地 = 读缓存 + 生成端**：读走缓存、断网可用；写走"回写钉钉"。
- **出正式报告需联网**（领全公司唯一编号，见 §3①）；离线只出草稿/预览。

## 3. 已定决策（与用户逐条敲定）

**① 报告编号：出正式报告在线领全公司唯一递增号。**
号由钉钉中心发；离线只能出草稿（无临时号、无回填、无冲突）。
*精化（2026-07-17）*：领号时机提前到**实勘开始**（估价师手机领号、绑定整个项目）；
**允许跳号**（领了没出报告即跳空，全公司递增本就允许）。

**② 台账：整份自洽快照上钉钉、append-only、当权威底账。**
钉钉存的每条台账内嵌当时的基础表知识/实例/方法/权重/结果（铁律 #5 快照自洽），
**单独就能复算**、谁也改不了。同步**只追加、绝不改已存条目**（守 #4 的审计性）。

**③ 基础表/模板：中心发布制。**
指定"知识管理员"把基础表/模板导入并发布到钉钉成公司版本；估价师端**只读拉取缓存、选版本用**，
本地导入只影响本机、不自动上推。符合"系统只读知识"(#2) + 旧版永不覆盖/指纹当版本(#8)。

**④ 实例库：自由贡献 + 留痕。**
估价师加实例即同步进公司库（记谁加的/何时）；用时估价师自负把关（选哪三条由人定，#7），
软校验（规模/离散度）只提示不阻断。实例是事实观测、越全越值钱，基本只增、冲突少。

**⑤ 审批：一期无闸。**
单份系数偏离**永远自由改、不卡**；将来最多只在 final（出正式报告）加一道，放二期
（`审批单号` 挂点项目里已留，叠加不返工）。

**⑥ 产物归档：台账快照 + 报告 docx + 协议书 docx 全上钉钉。**
成品原件（**含估价师现场照片**——照片只在 docx 里、不在快照里，故必须存 docx）可查可下。
协议书现不进台账，但作为产物存钉钉一份。

## 5. 代码落点（改动范围）

改动**圈在存储层**，engine/渲染/模板/金样/类别**一行不碰**：

- `LedgerStore`（append/get）、`InstanceStore`（load/save/add/remove/get）、
  `BaseTableStore`（load，指纹版本）、`DraftStore`（save/get/remove）各加一个
  "**本地缓存 ↔ 钉钉**"后端；**接口不变**，上层零改。
- 后端**做成可切换**（本地 / 钉钉）——保住断网兜底，也让测试继续跑本地后端。
- `src/paths.py` 已是存储位置的统一收口、env 可改，天然支持切换。
- 新增：编号服务客户端（向钉钉领号）、产物归档（docx 上传）、同步协议（append-only 回写）。

## 6. 分期

- **一期**：§3 ①~⑥ 全部（托管同步 + 统一编号 + 产物归档）。做完即达成"知识/记录归公司、编号统一"。
- **二期**：审批流（最多 final 一道）、权限细分、通知/统计。
- **专项**：移动端智能问卷（§7）、附件管理 + 渲染编排规范。

## 7. 规划中：移动端智能问卷（实勘采集，专项待细化）

用户设想：实勘时估价师手机**领报告编号 → 填问卷**；部分字段调**地图 POI 接口**（高德/百度周边搜索）
预填（附近公交、公共设施等），加速录入。

- **可行**：钉钉宜搭（低代码 + 连接器）或自建 H5 微应用（JSAPI 取定位/身份）可承载；
  POI 来自地图服务、非钉钉自带（具体能力以钉钉当前版本为准，落地时核）。
- **架构契合**：本质是把现有"表单输入"的实勘表字段搬到移动端，产出同样字段、喂**同一条下游管线**，
  引擎/渲染不改——是**新采集前端**，非新引擎。
- **三条红线（必须守）**：
  1. **只预填"事实"、不替下"判断"**：POI 事实（附近有哪些设施）可预填，须标来源+可改；
     由此推出的**因素档次**（交通便捷"好/中/差"）**不自动定**——估价师判断（#7/#8）。人在现场正好核对。
  2. **可复现**：POI 值经估价师确认后**存进快照**，出报告按存的那份渲染，**不在出报告时重查接口**（#5/#6）。
  3. **合规**：POI 查询把实勘坐标发第三方地图服务，属外部调用，须合规确认；不违反 #3
     （确定性数据检索、发生在采集阶段，非生成阶段模型调用）。
- **状态**：值得单独走一轮 brainstorm/spec，本文只钉定位与红线。

## 8. 开放技术问题（对接前须定）

- **钉钉承载层**：自建应用 + 后端 DB？钉盘存 docx？宜搭表？审批实例？—— 影响同步协议与鉴权。
- **鉴权**：钉钉企业身份 / OAuth 方式。
- **草稿是否上云**：建议**按人隔离、甚至不上云**（个人临时件、非公司资产）。
- **实例库并发贡献去重**：基本只增、冲突少，但需一个轻量去重/标重复策略（软提示不阻断）。
- **编号服务契约**：领号接口、跳号是否留痕、作废号处理。

## 9. 谁能拍板什么（承接 docs/README §8）

- 产品/工作流（分期、托管范围、编号时机、问卷形态）：用户（建设方）—— §3 已逐条敲定。
- 合规（数据出本机进钉钉、坐标发地图服务）：须贵司合规先行。
- 执业准则（因素档次判断、报告用语）：须执业估价师 —— 故智能问卷"不自动定档次"。
