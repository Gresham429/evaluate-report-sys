# 设计：钉钉多维表承载层（Notable 后端 + 报告编号）

- 日期：2026-07-18
- 状态：承载层已冒烟验穿（读/写 HTTP200，`tools/notable_smoke.py`）；本 spec 定"怎么落进代码"。
- 承接：`2026-07-17-钉钉全公司同步-design.md`（§3 决策不变），**把 §2b 的承载层从「宜搭」换成「钉钉多维表」**。
- 一句话：三个已就位的可插拔后端（Ledger/BaseTable/Instance），各写一个**打钉钉多维表**的实现，
  env 一开就把本地存储切成"公司多维表为权威 + 本地兜底"，并用多维表自动编号发全公司报告编号。

## 0. 为什么是多维表（承接冒烟结论）

- 宜搭 OpenAPI 卡专业版 5988/年，公司未订。
- 钉钉**多维表** 2024.04 起基础用量免费（扩容仅 198/人/年），OpenAPI 用同一套企业内部应用鉴权，
  **读/写已实测 200**。故承载层取多维表；"不自建后端/无服务器"约束保留（多维表是钉钉托管）。
- **免费额度：单个多维表约 2 万行。** 台账（一报告一行）、实例库（一实例一行）、基础表版本（一版一行）
  各占行——2 万行是容量红线，本设计加**行数软告警**（见 §6）。

## 1. 范围

**做（本轮）：**
1. 共享 **Notable 客户端**（`src/dingtalk/notable.py`）：token 缓存 + 多维表读/写/字段确保，HTTP 层可注入以便离线单测。
2. 三个 **Notable 后端**，实现既有 Protocol，行为对齐内存后端契约：
   - `NotableLedgerBackend`（append / iter_payloads，**只增不改**）
   - `NotableBaseTableBackend`（版本不可变 + 索引只追加）
   - `NotableInstanceBackend`（整库 load / upsert-by-编号 save，**不删**）
3. **可切换**：env `承载后端=多维表` 时三个 Store 默认走 Notable，否则本地（默认）。断网/未配置一律回本地。
4. **报告编号领号**：`领号()` 从台账多维表的"自动编号"字段取全公司唯一递增号（§3①，允许跳号）。
5. 两层测试：假客户端**单元测**（进 497 套件、离线确定性）+ **真机冒烟**（打真多维表跑通）。

**不做（各自要独立设计，明确延后）：**
- 钉钉登录鉴权 + 按人裁剪缓存（§7b，动整个桌面 app 的会话模型）。
- 成品 docx 归档到钉盘/附件（§3⑥，涉及钉盘 API + 附件流）。
- 权限细分 / 审批（二期）。
- 把领号接进 `web/app.py` 出报告流程的 UI 联动（本轮给出 `领号()` + 单测 + 冒烟；接 UI 放紧接的下一小步）。

## 2. 架构

```
              src/dingtalk/notable.py   ← 共享：token 缓存 + notable REST（list/insert/ensure_field）+ 领号
                        ▲
        ┌───────────────┼───────────────┐
NotableLedgerBackend  NotableBaseTableBackend  NotableInstanceBackend   ← 各实现既有 Protocol
        └───────────────┼───────────────┘
                        │  由 src/dingtalk/factory.py 按 env 选：多维表 / 本地
                        ▼
        LedgerStore / BaseTableStore / InstanceStore（__init__ 的 `backend or 默认后端(path)`，仅 3 处改）
```

- **HTTP 可注入**：`NotableClient` 把"发一个 HTTP 请求"收成一个可替换的 `transport` 可调用对象。
  单测传假 transport（返回预置 JSON），零网络、确定性；真机传真 urllib transport。
- **凭据来源**：`.env`（已 gitignore）——沿用冒烟那套 `YIDA_APP_KEY/SECRET` + 每个 Store 一组
  `baseId/sheetId/operatorId`。配置读取收在 `src/dingtalk/config.py`。

## 3. 数据映射（多维表行 ↔ payload）

各 Store 搬的是**不透明 payload dict**（序列化归各 Store，铁律 #5 不进后端）。多维表行的映射：

- **整份 payload 存一个长文本字段 `快照`（JSON 字符串）**——不把 payload 摊成多维表列，
  故 payload 结构演化不牵动表结构；这也是三个后端最简单、最稳的统一映射。
- 另存**索引/键字段**便于人肉浏览与按键查：
  - 台账：`记录号`（键）、`报告编号`、`类别`、`生成时间`、`经手人` + `快照`。
  - 基础表版本：`键`=`{类别}|{指纹}`、`类别`、`指纹`、`导入时间` + `内容`(=版本 JSON)；另一张索引表或同表用 `种类=版本/索引` 区分（见 §3b）。
  - 实例库：`编号`（键）+ `实例`(=实例 JSON)。
- **字段自备**：客户端 `ensure_field(base, sheet, name, type)` 首次写前确保字段存在（多维表建字段接口）；
  没有建字段权限就冒烟报错、改为请用户手动加列（最小 1~2 列）。
- **读**：list 全表（分页 nextToken 兜到底），逐行取 `快照`/`内容`/`实例` 反序列化。

### 3b. 基础表两件事一张表还是两张

`BaseTableBackend` 要存"版本内容(按类别+指纹不可变)"和"版本索引(只追加)"。多维表实现：
**一张表、两类行**，用 `种类` 字段区分 `版本`(带 `内容` JSON) 与 `索引`(带 `导入时间` 等)。
`version_exists` = 查有无 `种类=版本 且 键=类别|指纹` 的行；`write_version` 只在不存在时插；
`read_index` = 取所有 `种类=索引` 行。简单、少一张表配置。

## 4. 报告编号（§3①）

- 台账多维表加一个**"自动编号"字段** `报告序号`（多维表原生，行创建即自增、允许跳号——正合 §3①）。
- `领号()`：在台账表插一行"占位/领号"记录 → 读回该行的 `报告序号` → 组装成 `正恒评报字[YYYY]第{序号}号`。
  **待验**（冒烟阶段确认）：自动编号在 insert 响应里能否直接拿到，还是要再 list 读回。
- 离线：领不到号 → 只出草稿（§3① 原则不变）。本轮只交付 `领号()` + 测试，不接 UI。

## 5. 可切换与默认（不碰 app.py 的 15 个构造点）

- 三个 Store 的 `__init__`：`self._backend = backend or 默认后端(path)`，`默认后端` 来自
  `src/dingtalk/factory.py`：env `承载后端 == "多维表"` 且该 Store 的 notable 配置齐 → Notable 后端；
  否则 `LocalFileXxxBackend(path)`（**今日行为一字不变**）。
- `conftest` 不设 `承载后端` → 全部测试仍走本地（tmp）。契约测试显式传 `backend=` 亦不受影响。
- 断网/配置缺失/任何 Notable 构造异常 → 记 warning、回退本地后端（"断网仍能读缓存/出草稿"）。

## 6. 铁律与容量

- #4 只增不改：`NotableLedgerBackend` 无 update/delete（契约测试 `test_backend_has_no_mutation_api` 同款守）。
- #5 快照自洽：整份 JSON 存一格，一行离开库能独立反序列化。
- #8 旧版永不覆盖：`write_version` 只在 `version_exists` 为假时插。
- #4 延伸：`NotableInstanceBackend.save` **只增/改不删**——共享公司库里本地删除不该删公司数据（§3④ append 精神）。
- **容量软告警**：客户端 list 时若某表行数 ≥ 18000（2 万的 90%），logger.warning 提示接近免费额度。
